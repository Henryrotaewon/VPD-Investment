# FAST 주문 없는 포착·추적 v1

독립 실행 프로그램 `magi1.fast_observe`. VPD·지표가속 원장/설정은 읽거나 변경하지 않는다. 주문·텔레그램 모듈을 호출하지 않는다. 배포·자동실행 연결은 하지 않았다.

실행 예:

```bash
python -m magi1.fast_observe --db /data/fast-observe/observe.sqlite3 --duration 3600
```

별도 영속 디렉터리에 실행하고 한 프로세스만 사용한다. `aiohttp`는 기존 의존성이다. duration은 1~86400초; 종료 후 외부 스케줄러가 필요하다. 실제 네트워크 연결 및 Railway 부하는 아직 검증하지 않았다.

## 후보 규칙

업비트 KRW 전체를 관찰한다. 경고·스테이블 종목도 관찰만 하며 매수 적격으로 간주하지 않는다. trade와 독립 orderbook(level=0)을 구독하고 수신 시각의 완료10초 구간으로 판정한다.

- 최신 완료5분 거래대금 / 직전10일의 동일5분 평균 >=2
- 완료10초 거래대금 / 바로 앞60초의10초 환산 평균 >=3
- 매수 주도 거래대금 비중 >=65%, 체결 >=20건
- 깊이로 정규화한 최우선 호가 OFI >0, 체결·호가 신선도2초 이내
- 겹치지 않는10초 구간 두 번 연속 충족
- 상대거래대금, 순매수대금, 종목코드 순으로 선정; 동시에 추적 최대5개, 종목별 UTC일(한국09시 경계)1회

정확한 역사적 같은 시간 자료가 없으면 `BASELINE_WARMUP`이다. 기본 실행은 관찰한 완전한5분 구간을 쌓으므로 **기준자료 확보에10일 이상이 필요**하다. 임의로 짧은 표본이나 일일 전체 거래량으로 대체하지 않는다. 과거5분봉 초기 적재는 아래 fast_bootstrap 절차를 사용한다.

이 수치들은 해외 연구를 참고한 자체 검증 가설이며 검증된 매매 규칙/수익률이 아니다. 09시 개장 전용 전략이 아니라 종일 이동 구간 관찰이다.

## 기록과 복구

SQLite: baseline(최근11일 동일시간 기준), events(10초 WINDOW는5분, 기타 진단24시간 보관; CAPTURE 유지), captures(보존), outcomes(보존). 원체결·전체호가를 디스크에 계속 저장하지 않는다. 수신이 없는 정상 연결 구간은 거래대금0으로 기록하고, 연결 끊김/프로세스 지연 구간은 재준비한다. 재시작 후 당일 포착 중복을 막고 미완료 추적은 이어간다. 정책이 다른 DB 재사용을 차단한다.

포착 이후1·3·5·15분의 최초 신선한 체결을 기록한다. 목표시각 이후10초 안에 없으면 MISSING으로 남긴다. 가격 변화율은 포착 기준가 대비 관측값이며 모의 체결 수익률/순손익이 아니다. 호가·수수료·슬리피지 기반 매매 시뮬레이션과 MFE/MAE는 후속 작업이다. 포착 당시 최우선 매수/매도호가도 보존한다.

60초마다 콘솔 상태(연결수/종목수/포착수/추적결과/기준자료수)를 출력한다. 텔레그램 화면은 아직 연결하지 않았다.

## 초기 적재 및 보관 구조 (10:05 요청 반영)

`magi1.fast_bootstrap`을 추가했다. 포착 프로세스를 시작하기 전에 별도 실행한다. 기본은 업비트 KRW 전종목을 조회하며 종목별 기존 기준자료/상세봉에 없는 구간만 역방향 페이지로 요청한다. 최대200개/요청, 요청간격0.22초, 종목당32페이지 한도,418 즉시중단/429 제한재시도. 부족 이력은 COMPLETE로 표시하지 않는다. 전종목 완충 시 대략 수천 요청이 필요하며 네트워크 상황에 따라 시간이 걸린다.

```bash
python -m magi1.fast_bootstrap --db /data/fast-observe/observe.sqlite3 --archive-dir research/five_asset_reentry_20260910/data
```

위 archive-dir은 해당 연구파일을 가져온 경우에만 사용한다. 이 기능 브랜치에는 연구 원본을 중복 복사하지 않았다. 기존 파일이 없으면 옵션 없이 API 적재가 가능하다. 다운로드 오류는 실패로 종료하고 이미 커밋한 적재분은 유지한다. 재실행은 나머지 구간부터 채운다. 과거 기준시각이 기존자료보다 오래되면 중단한다. 관찰자와 초기 적재를 동시에 실행하지 않는다.

- baseline: 오늘 + 직전10일의 종목·5분별 거래대금 스칼라
- recent5m: 최근24시간 OHLCV와 거래대금·출처
- imports: 재사용 원본 경로·SHA256·사용 행수,11일 보관
- API에서 반환된 가장 오래된 봉과 exclusive 요청시각 사이에 실제로 빠진 구간만 무거래0으로 인정한다. 이때 상세 OHLC는 NULL이며 가상 가격을 만들지 않는다. 응답이 비어도 상장 이전 이력을0으로 만들지 않는다.
- 완료되지 않은 현재5분봉은 제외한다. 원자료는 검증 후 필요한 필드만 저장하고 새 원본 복사본을 만들지 않는다.
- 포착기에서 완전히 관측한5분 구간은 최근 상세자료와 거래대금을 갱신하고,24시간/10일 경계 밖 자료를 제거한다. LIVE_RECEIVE_TIME(수신시각 구간)과 ARCHIVE/API(거래소 봉시각) 출처를 구분한다. 수신지연으로 미세한 차이가 생길 수 있어 재적재 시 API값을 우선하며 불일치는 BASELINE_RECONCILED로 기록한다. 이는 거래소 봉과 완벽히 동일한 실시간 집계를 주장하지 않는다.
- 반복 보관으로 SQLite 파일 크기가 즉시 줄지는 않지만 삭제된 페이지는 재사용한다. WAL 체크포인트를 수행하며 원본 체결·호가를 지속 저장하지 않는다.

실행 확인: 2026-09-26 10:05 KST cutoff, 기존5종목 자료에서 거래대금12,229행/최근24시간 상세968행을 오프라인 초기 적재했다. DB831,488바이트. 이는 전종목 완성본이 아니라 기존자료 재사용을 실제 확인한 부분 적재다. 과거 연구자료는 당일02:55까지만 있어 최신구간 및 무거래 여부 확인을 위한 API 보완이 필요하다. 기타 기존 연구5분봉은 이번 보관기간보다 오래되어 재사용 대상이 아니었다.

검증: `python -m unittest tests.test_fast_observe tests.test_fast_bootstrap -v` (8개 통과). 초기 적재의 중복/미래봉제외/24h정리/기존구간요청회피/무거래판정/이력부족을 추가 확인했다. 이 실행환경에서 Upbit 직접접속은 제한되어 전종목 API 적재 및 실제 스트림 부하 검증은 미완료다.

## 운영 연결 (10:23 사용자 승인)

MAGI2 시작 시 독립 supervisor가 /data/magi2/fast-observe DB를 사용한다. 초기 적재 → 30분 관측 → 누락 보완 순서로 반복한다. 보완 중에는 포착을 중지하여 bootstrap과 observer가 동시에 원장을 변경하지 않는다. 이전 LIVE_RECEIVE_TIME 구간도 API로 재확인한다. 요청간격은0.4초로 낮춰 기존 스캐너 부하를 고려한다. 실패하면 진행분 보존 후60초 대기·재시도한다. 자식 프로세스에는 거래소/텔레그램/GitHub 비밀정보를 전달하지 않는다.

텔레그램 `⚡ FAST 포착·추적` 또는 `/fast_watch`: 기준자료 검사 진행/완비·미완비 수, 최신5포착 및1/3/5/15분 변화,24h연결·처리지연수, 추적누락수를 조회한다. 자동 포착 메시지는 보내지 않고 사용자 조회에 응답한다. 지표가속 기존 `/fast` 호환 명령은 그대로다.

새 연결은 과거10초 확인을 승계하지 않는다. 프로세스20초 초과 지연은 관측을 초기화한다.2초 초과 오래된 메시지는 사용하지 않으며 진단 로그는 종목별 분당1회로 제한한다. 목표시각 이후10초 내 가격이 없으면 MISSING 처리하고 이후 가격으로 덮어쓰지 않는다. 지속적인 재접속 실패는 감독자가 다시 시도하며 UI의 갱신 경과시간으로 감시한다. 정기 보완 기간의 추적 공백도 누락으로 남는다.

로컬18개 테스트 통과(관측/초기적재/UI/기존 지표가속). 배포 실측은 별도 운영 로그로 확인한다.

공유500MB 볼륨 보호: 진단은24시간만 유지하며 잔여공간64MiB 미만이면 적재/관측을 중지하고 상태를 재시도로 표시한다. 기존 계좌 자료를 삭제하지 않는다.


## 13:17 요청 — 관측을 유지하는 종목별 보완

기존30분 관측/전체중지 보완 교대를 폐지한다. 서비스는 `python -m magi1.fast_observe --continuous --repair` 하나를 계속 실행한다. 초기 이력이 없는 경우에도 WebSocket을 즉시 연결하고 준비된 종목부터 판단한다. `magi1.fast_repair`는5분 간격으로 부족한 기준자료와 LIVE_RECEIVE_TIME 값을 보완한다. API 왕복만 별도 스레드에서 처리하고, SQLite 읽기·쓰기와 실시간 판정은 이벤트 루프 한 곳에서 순서대로 처리한다. 응답 한 페이지 단위로 커밋하므로 HTTP 대기 중 실시간 체결과 추적 가격 수신을 계속한다.

- 현재 신호에 필요한 최신 완료5분과 과거10일 동일시간 기준이 없는 종목만 신규 포착을 막는다. 관련 없는 과거시간 상세봉 보완은 정상 종목 포착을 막지 않는다.
- 기준자료 복구 뒤 기존 확인 상태는 폐기하고 두 번의 새로운10초 확인을 요구한다. 과거 봉으로 수급/체결/추적 결과를 소급 생성하지 않는다.
- 특정 종목의 API 실패는 그 종목 재시도 상태로 남기고 다음 종목을 보완한다.429/418은 REST 작업만 대기하며 정상 WebSocket은 유지한다. 짧은 상장이력 등 미완비종목은30분 후 재점검한다.
- 일부 종목의 잘못된 체결/호가 메시지는 그 종목의 관측창만 재준비한다. 실제 공용 연결이 끊기면 해당 연결 그룹은 재접속하고 다른 연결 그룹은 유지한다.
- 텔레그램은 관측 보고와 보완 진행을 별도로 갱신하며 현재 보완 중/포착 대기 종목수를 표시한다. 보완 로그가 갱신돼도 실시간 관측 보고가120초 이상 늦으면 별도 경고한다.
- 공간64MiB 미만, 전체 프로세스 장애 등 공통 장애는 계속 안전 정지한다. 종목별 분리로 모든 종류의 중단이 없어지는 것은 아니다.

검증: 느린 API를 대기시키는 동안 다른 종목 체결10건과1분 추적값이 계속 기록됨, 실패 종목 다음 정상종목 처리, 복구시 새 확인, 종목 메시지 오류의 격리. 기존 회귀 포함23개 로컬 테스트 통과. 기존4포착/16추적 중6누락은 그대로 보존하며 누락을 보완 봉으로 바꾸지 않는다.
